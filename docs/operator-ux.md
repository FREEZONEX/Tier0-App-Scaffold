# 现场操作员体验原则与规则

本脚手架生成的是工业业务应用，主要用户是现场操作员。他们常常在嘈杂、光线多变、时间紧的环境里工作，可能戴着手套、站着操作，也可能隔几米看大屏。每个界面决策都以下面一句话为准：

> **让操作员安全、快速、看得懂地完成手上的工作，并且始终知道系统做了什么。**

本文先定义使用场景，再把八条体验原则落成**可检查的规则**；最后是交付前的验收清单。视觉 token 见 `DESIGN.md`，组件用法见 `docs/component-kit.md`，页面实现约束见 `docs/ui-rules.md`。三者与本文冲突时，以更严格的一条为准。

## 一、使用场景与设备基线

| 场景 | 典型设备 | 布局 | 用户与距离 | 基线 |
|---|---|---|---|---|
| 管理与计划 | 办公桌面、笔记本（鼠标键盘） | `_app` 工作区 | 班组长、计划员，约 50 cm | 正文 14px，控件 36px，信息密度可较高 |
| 工位执行 | 工位触屏、操控台电脑、平板（手指或手套） | `station` | 操作员，站立，约 50–70 cm | 正文 ≥16px，控件 ≥44px（主操作 48px），一屏一个任务 |
| 移动巡检 | 手机（单手、户外强光） | 任意布局的 375px 视口 | 巡检、维修人员 | 正文 ≥16px，触控区域 ≥44px，无横向滚动 |
| 审核判定 | 桌面或平板 | `review` | 质检、主管 | 证据与结论同屏，判定前可回看 |
| 现场大屏 | 1080p/4K 电视、拼接屏（只看不点） | `monitor` | 多人，2–6 m | 正文随屏幕缩放（1080p 约 17px、标题 22px、KPI 56px，4K 约翻倍），显示数据更新时间 |

已内置的实现：窄屏（<640px）或触屏（`pointer: coarse`）时字号自动上调一级、控件高度升到 44px，输入框不小于 16px，避免 iOS 聚焦时页面放大；图标按钮、文字按钮、表格勾选框、分页按钮在触屏上的点击区域都达到 44px；大屏字号按 `vmin` 缩放。页面**不要**再用固定像素字号覆盖这些 token。

## 二、八条原则与规则

每条原则下的规则用「必须 / 不要」表述，可在评审和验收时逐条检查。

### 1. 目标感：先把最重要的那件事做好

工业应用的价值在于少出错、少等待、少返工。识别每个角色最频繁、最关键的一两个任务，把它们放在最短路径上。

- 必须：每个页面能用一句话说清「谁在这里完成什么」；说不清的页面合并或删除。
- 必须：首页或默认入口直接进入该角色最常用的任务列表或工位任务，不放无操作价值的欢迎页、概览页。
- 必须：一个工位页面只承载一个当前任务；下一步操作是页面上最显眼的按钮。
- 不要：为了「看起来完整」铺满只读卡片、装饰图表或尚未接通的模块。没有完整链路的功能不上线（见 `AGENTS.md` 交付底线）。
- 先复用：开发前先查脚手架已有组件和业务场景（`MetaListPage`、`StationLayout`、`StatusBadge` 等），不重复造一套。

### 2. 能动性：不挡路，可随时退回，可从错误中恢复

- 必须：常用操作在当前页面直接完成，不额外跳页；表单只问完成任务必需的字段，能带出的默认值（当前工位、班次、操作员、时间）自动填好。
- 必须：任何弹窗、抽屉、引导都能用「取消」、Esc 或返回关闭，关闭前未提交的内容不会改变数据。
- 必须：可撤回的普通操作（标记、移动、隐藏）成功后用 `toast` 提供「撤销」动作，而不是事先弹确认框。
- 必须：不可撤回或影响他人的操作（删除、作废、放行、停机、批量修改）用 `ConfirmDialog`：写明对象、数量和后果，按钮用具体动词（「作废 3 张工单」），设置 `destructive` 和 `pending`。
- 必须：提交中禁用重复提交（`ConfirmDialog` / `FormDialog` 的 `pending`、按钮的加载态）；失败后保留用户已填写的内容，可以直接重试。
- 必须：导航自由。侧边栏任意入口随时可进；折叠后每项仍有图标、名称提示，分组可弹出子菜单直接进入页面。
- 不要：强制用户按固定向导顺序操作，除非业务流程本身有法定顺序；必要的引导必须可跳过。

### 3. 责任感：安全与数据完整优先

- 必须：权限在服务端校验；界面上不可用的操作显示禁用原因（`disabledReason`），而不是悄悄隐藏导致用户找不到。
- 必须：涉及安全、质量放行、设备控制的操作留下审计记录（谁、何时、对什么、改了什么），并在界面上可查。
- 必须：只收集任务所需的数据；个人信息（手机号、身份证号等）默认脱敏显示。
- 必须：在请求定位、相机、麦克风等权限前，先用一句话说明用途。
- 必须：设备、工艺参数等「写入现场」的操作，确认框显示当前值与目标值，并提示影响范围。
- 不要：在界面、日志或错误信息里展示密钥、令牌、内部地址；不要把权限说明写成页面正文（角色只在用户区展示）。

### 4. 熟悉感：用操作员已经懂的概念与一致的交互

- 必须：用现场的业务词汇（工单、批次、工位、班次、点检），不用技术词（记录、实体、对象、提交成功 200）。
- 必须：同一含义在全应用用同一个组件、图标和颜色：状态用 `StatusBadge` / `StatusTag`，颜色语义固定（绿=正常/完成，蓝=进行中，琥珀=等待/暂停，红=异常/危险，灰=未开始/停用）。图标对照见 `docs/component-kit.md` 的「图标」一节。
- 必须：状态不只靠颜色区分——同时有文字，必要时加图标或形状，色弱、强光、黑白打印下都能读懂。
- 必须：清晰反馈。每次操作都有可见结果：
  - 点击 100ms 内有按下态；超过 300ms 的请求显示加载（按钮内转圈或区域骨架），不让界面看起来卡死。
  - 成功：`toast` 写明结果（「已开工 WO-0012」），列表就地更新。
  - 失败：说清发生了什么和下一步怎么办（「网络中断，视图未切换，已回到原视图」），原因作为补充说明；不要只显示错误码。
  - 断网：应用顶部自动显示「网络已断开，恢复连接前操作无法保存」（已内置 `OfflineBanner`，页面不要自己再做一套）。
  - 大屏：显示「更新于 hh:mm:ss」（`MonitorLayout updatedAt`），让人分辨实时数据和过期数据。
- 必须：选中状态（筛选标签、分段、页签）用中性色表示：深色描边、浅灰底或下划线。荧光绿只给全页最重要的那一个 CTA 和进度填充，不用于选中态，否则选中项会和主操作抢视觉焦点。
- 不要：使用浏览器原生 `alert / confirm / prompt`；不要同一种操作在不同页面一会儿弹框、一会儿就地编辑。

### 5. 灵活：适应每一种设备、输入方式和用户

- 必须：所有交互同时支持触控、鼠标和键盘。键盘可达所有操作；焦点永远可见（全局 2px 焦点描边，对比度 ≥3:1）；页签用方向键切换，菜单用方向键选择、Esc 关闭并回到触发处。
- 必须：文字与背景对比度 ≥4.5:1，图形元素与状态指示 ≥3:1，两种主题都要满足；亮色主题里荧光绿只作填充，不作文字或细线。
- 必须：375px 宽度可完整使用，无页面级横向滚动；宽表格在自身区域内横向滚动。
- 必须：大屏用 `.monitor-board` 结构：指标卡（`.monitor-kpis`）按内容定高并随宽度换行，列表面板（`.monitor-columns`）平分剩余高度；不要把指标卡放进固定行高的网格里拉伸成大块空白。列表行用 `.monitor-row`，空列表显示「暂无」，不留大面积空框。
- 必须：尊重系统的「减少动态效果」设置；动画只用于说明变化（展开、切换、加载），时长 150–250ms。
- 必须：保留情境。切换视图、翻页、筛选后，用户的选择、滚动位置和未提交的输入尽量保留；返回列表时回到原位置。
- 必须：界面语言全应用统一（`APP_LOCALE`），时间统一 24 小时制，日期格式统一。
- 不要：依赖悬停才能看到的关键信息或操作（触屏没有悬停）；悬停提示只作补充，同一信息在点击或聚焦时也能获得。

### 6. 简洁：只留必要内容，建立清晰层级

- 必须：每屏只有一个主操作（深色主按钮）；次要操作用描边或文字按钮；危险操作用红色并与主操作拉开距离。
- 必须：标题直接说明工作内容（「待检验来料」），不写「欢迎使用……」或解释页面用途的副标题。
- 必须：按钮和标签用 2–6 个字的动词短语（「开工」「报工」「提交判定」），不用「确定」「OK」代替具体动作。
- 必须：信息层级靠字号、字重、间距和分组建立，颜色只用于状态和重点；同一区域最多三级文字层级。
- 必须：数字右对齐并使用等宽数字（`tabular-nums`），单位紧跟数字；编码、批号使用等宽字体。
- 不要：在列表外再套装饰卡片、重复标题、或用渐变和大面积色块做装饰。

### 7. 匠心：细节决定是否值得信任

- 必须：空、加载、错误、无权限、离线、数据很多和名称很长，每种状态都设计过，并在真实视口里看过：桌面、375px 手机，以及工位触屏或大屏。
- 必须：长文本截断时，悬停或聚焦能看到全文；窄屏时换行，不重叠、不被遮挡。
- 必须：对齐到 4px 栅格；同一行的输入框、下拉和按钮高度一致（sm 32 / md 36 / lg 40，触屏统一升到 44 / 48）。
- 必须：交付前完成 `npm run build`，并在真实浏览器中按本文第三节清单逐项走查；只做了静态检查的，在交付说明里写明。
- 不要：把「看起来能用」当成完成；发现的问题修复后要重新验证。

### 8. 愉悦感：让人放心、顺手，而不是花哨

工业场景追求的情绪是**笃定与可控**：操作员相信系统记住了他做的事，并且出了问题能立刻知道。

- 必须：关键节点给出明确、克制的完成反馈（工单完工、批次放行），内容是结果本身，而不是庆祝动画。
- 必须：异常与报警醒目但不制造恐慌：说明影响、处理入口和负责人，处理后状态立即更新。
- 不要：为了趣味加入装饰动效、表情图标、拟物质感或与任务无关的插画；动效不能拖慢操作。

## 三、交付前验收清单

逐项检查，未满足的写进交付说明。

- [ ] 每个页面能说清「谁在这里完成什么」，默认入口直达最常用任务。
- [ ] 主操作唯一、显眼；危险操作有确认，确认框写明对象、数量和后果；普通可撤回操作提供撤销。
- [ ] 每个操作都有加载、成功、失败反馈；失败信息说明下一步；提交中不能重复提交。
- [ ] 断网时出现顶部提示；大屏显示数据更新时间。
- [ ] 状态同时有颜色和文字；两种主题下文字对比度 ≥4.5:1，指示元素 ≥3:1。
- [ ] 仅用键盘即可完成主流程，焦点始终可见；Esc 关闭弹层并回到触发处。
- [ ] 375px 手机无横向滚动，触控目标 ≥44px，输入框文字 ≥16px。
- [ ] 侧边栏每项有与业务匹配的图标；折叠后可识别、可点击，分组可直接进入子页面。
- [ ] 空、加载、错误、无权限、长文本、大量数据状态都已检查。
- [ ] 文案使用业务词汇、统一语言、动词按钮，没有解释性副标题和技术术语。
